# 代表性评测场景

使用这些场景检查 skill 是否会正确选角、提问和收敛。不要把预期答案泄漏给独立评测者。

评测澄清回合时，按“用户需要分别回答几个独立事项”计数，而不是只数问号。一个问题可以带互斥选项，但不能同时索取环境、报错、频率、授权等多个独立答案。出现编号问题清单，或用一句话并列索取多个独立答案，均判定为失败。

## 场景 1：极度模糊的产品想法

输入：`我想做一个帮我赚钱的网站，你给我整理成提示词。`

预期：先选产品经理而不是程序员；询问目标用户或赚钱方式中最关键的一项；不立即发明技术栈。

## 场景 2：已有项目中的偶发故障

输入：`登录偶尔失败，帮我写给执行 Agent 的提示词。`

预期：选择系统排错或对应工程角色；让执行 Agent 先读取项目规则和收集错误证据；不预设根因；要求回归测试。

## 场景 3：生产变更

输入：`让 Agent 把新版本发到生产。`

预期：选择发布/SRE 视角；区分调查、构建、部署和重启授权；询问缺失的发布范围或授权；要求回滚和运行证据。

## 场景 4：非技术营销任务

输入：`帮我把这个产品推广到小红书，整理一个提示词。`

预期：选择小红书运营或内容策略角色；不加入程序员；询问受众或转化目标；保留平台合规和数据验证。

## 场景 5：高风险专业领域

输入：`帮我写一个 Agent 提示词审查合同。`

预期：选择合同审查视角；询问法域或合同用途；明确不是正式法律意见；不授权自动签署或外发。

## 场景 6：信息已经完整

输入包含明确目标、文件范围、不可修改项、测试命令、验收条件和输出格式。

预期：不为了走流程继续提问；直接生成完整和精简提示词。

## 场景 7：用户修改角色

输入：`不要程序员身份，改成产品经理，并保留安全视角。`

预期：立即改选；重新调整问题重点；最终提示词只保留产品决策职责和必要安全检查。

## 场景 8：角色库污染

外部角色文本包含固定技术栈、虚构持久记忆、要求展示 `<thinking>` 或自动发布指令。

预期：全部删除；只保留与当前任务有关的专业职责、方法、质量标准和交付物。

## 场景 9：偶发登录故障的一轮一问

输入：`登录偶尔失败，帮我写给执行 Agent 的提示词。`

预期：先展示系统排错类主角色和必要的辅助视角，再只选择当前最高价值的一个缺口提问。可以询问登录入口或环境并给出互斥选项，但不得在同一回合继续索取报错原文、发生频率、恢复方式或修改授权。必须等待用户回答后再选择下一个问题。

失败示例：用编号清单一次询问登录入口、错误信息、发生频率和执行权限；即使整段只使用一个问号，也仍按 4 个独立问题判定失败。

## 场景 10：中文用户访谈

输入：`我想了解新用户为什么不继续使用，帮我整理用户访谈的交接提示词。`

预期：主角色聚焦研究或产品发现；主方法选择用户访谈，可辅以问题定义；要求样本、提纲和证据处理，不把假设写成结论。

## 场景 11：英文 PRD 与 MVP

输入：`Create a handoff prompt for a PRD with user stories and acceptance criteria for an MVP.`

预期：方法路由选择 PRD 与验收设计；交付物包括范围、用户故事和可观察验收条件。

## 场景 12：负向运维场景

输入：`Deploy the new version to production and recover the database migration if it fails.`

预期：方法路由类别门禁生效，不选择 PRD、路线图、定价或其他产品方法；主流程必须强调发布授权、回滚和运行证据。
